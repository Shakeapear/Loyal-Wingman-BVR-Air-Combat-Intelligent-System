# 阶段二 2.6 引导策略行为树 实现与测试报告

> 范围：步骤 2.6 最小可运行版本（D2.6-1/2/3/4）。未改 DRL 网络/训练/JSRL 训练循环，未改 `common/bvr_combat_env.py` 物理、奖励、终止逻辑，未执行 2.7 的 20 组态势/存活率验收。
> 结论：**两级优先级行为树可完整执行；OODA 覆盖 100%；GuideInterface 接口通过单测；3 seeds × 240 步联调 0 安全违规、0 逻辑错误；行为树 47 项、三套全量 150 项测试通过。**

## 1. 架构

```
                 ┌────────────────────────────────────────────┐
                 │ GuideInterface（D2.6-3）                   │
                 │ active + current/max_guide_steps           │
                 │ get_action → (action, is_guided) | (None,F)│
                 └───────────────┬────────────────────────────┘
                                 │ 引导期内
                                 ▼
                 ┌────────────────────────────────────────────┐
                 │ 战术执行子树（D2.6-2，py_trees，OODA）      │
                 │ Human_Command / Self_Defense / Fuel_Return │
                 │ BVR_Engagement(Detection/Engagement)       │
                 │ Default_Patrol                             │
                 └───────────────┬────────────────────────────┘
                                 │ 每步 Dict 动作
                                 ▼
                 ┌────────────────────────────────────────────┐
                 │ 边界约束守卫（D2.6-1，最高优先级）          │
                 │ 6 类规则：覆盖/限幅，不可被 Selector 绕过   │
                 └───────────────┬────────────────────────────┘
                                 ▼
                    BVRCombatEnv（JSBSim，1 Hz 决策）
```

### 优先级语义

- **第一优先级（边界约束）**：`BoundaryConstraints.apply(action, bb)` 在每步战术树动作之后执行，直接改写 `flight` 通道；不是行为树内可被 Selector 绕过的条件分支。
- **第二优先级（战术执行）**：py_trees 反应式 Selector 按 Human_Command → Self_Defense → Fuel_Return → BVR_Engagement → Default_Patrol 顺序求值。
- 两棵子树均通过 `llm_bt.executor` 的黑板/动作回路接入，复用 2.5 的 `_bank_to_heading`/`_hold_altitude`/`_hold_speed`/录制链路。

## 3. 边界约束（D2.6-1）

文件：`引导策略行为树/llm_bt/boundary_constraints.py`。阈值默认对齐 `common/bvr_combat_env.DEFAULT_CONFIG`（构造时可注入 `env_cfg`）。

| 约束 | 触发条件 | 退出（滞回） | 动作覆盖 |
|------|----------|--------------|----------|
| min_altitude | AGL < 500 m | AGL > 650 m | 满油门 + 抬头（pitch ≤ -0.15），先改平机翼 |
| min_speed | v < 90×1.2 = 108 m/s | v > 118.8 m/s | 满油门 + 低头（pitch ≥ +0.12），减小坡度 |
| over_g | nz > 5.5 或 nz < -2.5 | nz ∈ (-2.2, 5.2) | 放松拉杆（±0.06）；roll/pitch 每步限幅 0.12/0.08 |
| max_speed | Mach > 1.65 | Mach < 1.60 | 收油门至 0，轻微抬头（pitch ≤ -0.04） |
| no_fly_zone | 圆形（距圆心 < R）或多边形（射线法） | 离开区域 | 朝“圆心/多边形质心 → 本机”方向转弯脱离，油门 ≥0.8 |
| fuel_low | fuel_frac < 0.20 | fuel_frac > 0.25 | 强制返航：朝原点、9000 m、250 m/s，油门 ≥0.75 |

实现细节：

- **覆盖优先级**：`min_altitude > min_speed > over_g > max_speed > no_fly_zone > fuel_low`；同时激活时只应用最高优先级动作，其余记日志。
- **滞回**：enter/exit 阈值分离，避免阈值附近抖动；触发/清除各写一条日志。
- **日志字段**：`step, constraint, event(trigger/clear), value, threshold, action_override`；`summary()` 输出 `boundary_trigger_count`、`boundary_override_steps`、`per_constraint`。
- **禁飞区**：默认空列表；圆形与多边形均支持；多边形脱离按质心方向近似，报告 §6 说明。
- 不修改环境物理/奖励/终止逻辑，仅改本步动作。

## 4. GuideInterface（D2.6-3）

文件：`引导策略行为树/llm_bt/guide_interface.py`。

| API / 属性 | 语义 |
|------------|------|
| `GuideInterface(max_guide_steps=240, guide_active=True)` | 引导最大步数与初始激活状态 |
| `get_action(obs, guide_policy)` | 激活且未耗尽 → 调用 `guide_policy(obs)`，返回 `(action, True)`；否则 `(None, False)`；策略返回 None 不计数 |
| `update_guide_steps(new_max_steps)` | 课程式更新上限；设为 0 时停用引导；负数报错 |
| `reset()` | 每 episode 清零 `current_guide_step` 并恢复初始激活状态 |
| `exhausted` / `remaining_steps` | 引导是否耗尽 / 剩余步数 |
| `set_active(bool)` | 手动启停 |

接入点：`run_guidance_sim.run_episode` 每步以闭包 `policy(obs) → tick_once(..., boundary=guard)` 调用 `get_action`，引导耗尽后返回 `(None, False)` 并使用安全平飞占位（无 DRL 时的联调替代），保证接口语义可验证。`executor.tick_once` 新增可选 `boundary` 参数，默认 `None`，2.5 行为不变。

## 7. 限制与未完成项

1. **真实态势未自然触发边界约束**：3 seeds 正式联调中 6 类约束触发数均为 0（飞行包线内）；6 类约束的正确性由合成单测与 `--guard-demo` 禁区演示验证，未伪造触发。
2. **多边形禁飞区脱离方向按质心近似**：未实现最短边法向脱离；圆形区域为精确距离判定。
3. **单机环境限制**：`maintain_formation` 无僚机对象，按平飞处理；`has_human_command` 默认无外部输入；`SelectWeaponType` 无多武器槽，映射为 `has_weapon_remaining`。
4. **引导耗尽后的 DRL 接管**：本步骤不训练/接入 DRL，联调使用安全平飞占位；`get_action` 的 `(None, False)` 语义已由单测覆盖。
5. **2.7 未做**：20 组典型态势、LLM 树 vs 手写树对比、存活率 >80% 验收均未执行。
6. 真实联调 seed 33 的步数与 2.5 不同（54 vs 53），因战术树新增 Human_Command 分支与执行顺序差异，属正常现象。
